## Notes

1. **Claim 2 (TFCD to TFAT).** The first file is correct. Precise details:
   - The deprecation arrived in **Google Mobile Ads Unity plugin v11.3.0** (GitHub release dated 19 Jul, 3 months before today, so July 2026). It bundles Android GMA SDK 25.4.0.
   - The Unity API is `RequestConfiguration.AgeRestrictedTreatment = AgeRestrictedTreatment.Child`. The Android API is `setAgeRestrictedTreatment(AgeRestrictedTreatment.CHILD)`.
   - The old TFCD still works, because Google "applies the most conservative treatment" when both are set. It is deprecated, not removed.
   - On plugin versions below 11.3.0, `AgeRestrictedTreatment` does not exist, so TFCD remains the only option there.
   - The AdMob Families help page (answer/6223431) still tells mixed-audience apps to call `setTagForChildDirectedTreatment()`. It also requires "Android 20.6.0 GMA SDK or later" so the ad ID is not sent on child-tagged requests. Both statements are consistent with the deprecation, because the old method is functionally equivalent.
   - I could not find the exact Android SDK version that introduced `setAgeRestrictedTreatment()` on an official page. It is presumably 25.4.0 or earlier.

2. **Claim 4 is stricter than the first file implies.** The data-practices page says mixed-audience apps "may only transmit these identifiers from users that they know are adults."
   - "Transmit" covers any off-device destination.
   - In practice, AAID and hardware IDs must not leave the device unless an age screen has established the user is an adult.
   - The first file's plan (remove AD_ID, use child treatment on every request) is consistent with this.
   - App Set ID is explicitly encouraged for analytics. It is not listed among the prohibited identifiers.

3. **Claim 3b: Firebase.** No official Google or Firebase page states that Firebase Analytics or Crashlytics is approved, or not approved, for child-directed services.
   - The only related official statements are general: comply with COPPA (Crashlytics ToS), and use app set ID for analytics (Families).
   - The first file's "main residual uncertainty" assessment stands.

4. **Claim 7 reconciled.** November 1, 2025 was the original requirement start, per the blog. The current developer.android.com page (updated 2026-10-16) and the Play Console warning say updates that don't support 16 KB will be blocked from **February 1, 2027**.
   - Interpretation: an extension or grace period ran between those dates. The requirement is in force now ("must support"), and the hard block on updates starts February 1, 2027.
   - I did not find an official page that explicitly describes the extension. Some third-party blogs mention May 31, 2026, but no official source confirms it.
   - The first file's conclusion is correct.

5. **Claim 8: the first file's "UNCERTAIN / conflicting" note is wrong.**
   - The deprecation table lists the version being retired on each date. The banner states the resulting minimum. They agree.
   - **Today (2026-10-19), the minimum for new apps and updates is PBL 8.** Extensions for PBL 7 run until November 1, 2026.
   - PBL 8 is acceptable until August 31, 2027, extendable to November 1, 2027. After that, PBL 9 is required.
   - The first file's recommendation (PBL 8 or later) is correct.

6. **Claim 10: UGC and ghost runs (interpretation, not Google wording).**
   - UGC is defined as content that "users contribute" and that is "visible to or accessible by at least a subset of the app's users". A recorded run shown to other players fits that definition literally. That applies especially if the run includes player-chosen elements (names, free text).
   - If the label is auto-generated by the developer ("Rival #1234") and the run consists only of game actions, the user contributes no expressive content. The case is weaker, but the policy page gives no game-specific guidance either way.
   - If the UGC policy applies, the duties are:
     - terms of use accepted before contributing;
     - a definition of objectionable content;
     - moderation that is "reasonable and consistent with the type of UGC";
     - an in-app system for reporting and blocking objectionable UGC and users.
   - Because the policy says moderation is proportionate ("Different UGC experiences may require different moderation efforts"), runs with no free text plausibly need only light moderation. The in-app report/block mechanism is the safest thing to add if runs are attributable to players.
   - The UGC page also references children: an app with incidental sexual content must screen children out. That is irrelevant here.
   - The Families "social features" rules (in-app safety reminder, parental controls, adult action) apply only to sharing "freeform content" or communicating with large groups. These are already quoted correctly in the first file.

7. **Minor accuracy notes on the first file.**
   - Claim 5: confirmed verbatim. The full sentence on entire-screen ads continues "or interfere with normal use and do not provide a clear means to dismiss the ad".
   - The self-certified SDK policy states no minimum SDK version. It says SDKs "Must use the latest released, or soon to be released version" for the test app. The "19.0.0 or later" comes from the SDK list page (claim 1).
   - Nothing was found that contradicts the first file's quotes on target API, account deletion, or the mixed-audience neutral age screen.
